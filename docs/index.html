ECOM — a registry for unattended software estates

An anonymous open protocol · MCP · self-hosted · MIT

Agents draft and run the routine. One act belongs to a person.

ECOM is a registry served over the Model Context Protocol. Agents come and go; what persists is the record of what was observed, what was concluded, what was attempted, and what it cost.

The claim

No human workers. One human act.

Nobody writes the code, runs the migration, reads the crash report or files the finding. Machines do the work. A person does exactly one thing, and the protocol names it: approve_plan.

This is a boundary, not a boast. An agent may propose anything, attempt anything and record anything — but the gate that lets a plan run is a separate tool, and its own documentation forbids an agent from pulling it: call it on a person's instruction, never on your own judgement. Everything else is unattended.

What makes that survivable is bookkeeping, not cleverness. An agent has no memory between sessions; the registry has nothing but memory. Every design decision follows from that asymmetry — the record is the institution, and the agents are transient staff who consult it, add to it, and are forgotten.

Structure

Five registers, thirty-one tools

Every one is an MCP tool. There is no other way into the store — no REST side door, no direct SQL for agents.

Estates

What exists. Type, repository and branch, backend address, last known commit, and an append-only column of environment notes that no tool may overwrite.

list_projects · get_project · create_project · update_project · append_env_note · set_latest_commit

Agents

Who is at work. A name, a role, the model it runs on, capability tags, a state — idle, working, disabled — and a heartbeat, so a working agent can be told from a stalled one.

register_agent · list_agents · set_agent_status · heartbeat_agent

Tasks

What is being attempted. Work is assigned, planned, gated by a person, then run. Dependencies form a graph that refuses to close a cycle, and every attempt appends a result rather than replacing one.

assign_task · submit_plan · approve_plan · log_result · get_task · list_tasks · ready_tasks · add_task_dependency · remove_task_dependency · task_blockers

Signals

What was observed, unjudged. Crash rates, store verdicts, revenue lines, backend logs, manual notes — each with a deduplication key, so re-ingesting a week corrects the record instead of doubling it.

record_signal · list_signals · register_signal_source · list_signal_sources

Findings

What was concluded, and on whose evidence. A claim carries severity, confidence, a proposal and the identifiers of the signals beneath it. It closes only by a decision, and a rejection must state its reason.

create_finding · list_findings · get_finding · add_finding_evidence · decide_finding

The estate itself

system_status renders the whole holding in one call. create_backup snapshots the database and pushes it to a git remote if one is configured; snapshots also run on a timer, unasked.

system_status · create_backup

The chain

The registers are not five separate stores. Something is measured and becomes a signal. A signal is read and becomes a finding, carrying that signal's identifier as evidence. A finding is decided, and an accepted one becomes a task. The task is planned, the plan is gated by a person, and the run appends a result that never erases the attempt before it.

Rules

Seven rules, enforced in the store

Each is enforced at write time rather than described in a prompt. An agent that has read no prompt must still be unable to break them.

  1. Nothing enters twice.Every signal carries a caller-supplied deduplication key. The same key written again updates the row, so re-ingestion is always safe and nothing is double-counted.
  2. The record is added to, never overwritten.Each result appends; each environment note is timestamped and left standing. A task that failed four times before succeeding keeps all five rows.
  3. Nothing runs on an agent's own say-so.A plan runs only after the human gate, and re-submitting a plan voids any approval it already held.
  4. Work cannot wait upon itself.A dependency that would close a cycle is rejected at write time, so the ready set is always computable.
  5. A claim names its evidence.Findings carry the identifiers of the signals beneath them. Severity — how much is being lost now — and confidence — how directly it was measured — are separate fields, never conflated.
  6. A refusal is recorded as carefully as an approval.Rejecting is a normal outcome, not a failure. Rejected and resolved both require a written reason.
  7. No secret enters the record.Environment notes and source configurations are plain text and documented as plain text. Addressing only. Credentials live in the process environment or nowhere.

Running it

Self-hosting

An HTTP MCP server holding a single SQLite file. There is no cloud, no account and no operator. You run it, or it does not exist.

1 · Raise the server

# the registry keeps one file; everything else is disposable
ECOM_DB_PATH=/var/lib/ecom/registry.sqlite
ECOM_API_TOKEN=<64 hex characters you generate>
ECOM_BACKUP_REMOTE=<optional git remote for snapshots>

2 · Declare it once

{
  "mcpServers": {
    "ecom": {
      "type": "http",
      "url": "https://<your-host>/ecom/mcp/",
      "headers": { "Authorization": "Bearer <your token>" }
    }
  }
}

One token, one estate. Whoever holds it can write to the whole record — so rotate it deliberately, and mind the ordering: change it on the server first, restart, then change it in the client.

3 · Open the record

# the customary first four calls
system_status
create_project   name="…" type="mobile_app|web_app|website|internal_tool|ai_factory"
register_agent   name="…" role="…" model="…" capabilities=[…]
register_signal_source project="…" kind="crashlytics|analytics|store_reviews|backend_logs|manual"

Then instruct your agents to consult the record at the start of a session and add to it at the end. That instruction is the entire operating discipline; there is no other configuration.

Scope

What it gives, and what it will not

What you get

  • A memory that outlives the session, the model and the agent.
  • Findings ranked by what is being lost now, not by who raised them.
  • Re-readable sources: the same week ingested twice corrects itself.
  • A full retry history for every attempt, including the failures.
  • A dependency graph that answers what may start now.
  • Decisions with reasons attached, so settled arguments stay settled.
  • One file you can copy, snapshot and read with any tool that speaks SQL.

What it is not

  • Not a scheduler. It records work; it does not run it.
  • Not a secret store. Everything written is plain text, by design.
  • Not multi-tenant. One token, one estate, no roles.
  • Not a substitute for the human gate. The gate is the product.
  • Not a metrics platform. It holds the observations you chose to keep.
  • Not a service. Nobody hosts this for you.
